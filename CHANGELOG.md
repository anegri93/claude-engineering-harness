# Changelog

## Unreleased

- The engineering standard now says how work reaches the trunk. It covered how code is written, verified and reported and then stopped at the edge of the commit, so the one step where a repository's checks are supposed to run was left to habit — and habit pushes to the default branch. That is not a cosmetic gap: a `pull_request:` trigger in CI costs nothing to add, shows green in the settings page, and in a repository where everything lands on `main` directly it has never run before a single merge. This repository is the example: `.github/workflows/ci.yml` has carried a `pull_request` trigger the whole time, across 36 commits with exactly one merge commit, so the suite has only ever run after `main` was already broken rather than before. The new `## Branch and merge` section states the convention — one unit of work is one branch, one pull request, one merge commit; branch as `<type>/<kebab-slug>` with the Conventional Commits vocabulary so the branch name and the commit type cannot disagree; short-lived branches, and if one needs more than a handful of commits it was two branches; merge commits rather than squash, because the squash erases the boundary the history was recording. Two clauses keep it from doing damage where it does not belong: the repository's own convention wins, read from `git log --merges` and the merge settings rather than assumed, so a squash-only repository or one that requires a ticket number in the branch name is followed instead of overridden; and constraints on what belongs in one commit outrank the commit count, so a project that requires two files to move together is not split to hit a number. Deliberately not added: a CI job validating branch names and branch protection on the default branch. Both police a convention rather than follow one, and neither belongs in a standard that installs into every repository the user opens.

- The living baseline no longer goes blind to a task that edited through Bash. `refresh-baseline.sh` read exactly one source of changed files: the PostToolUse edit record, which Claude Code writes only for `Write`/`Edit`/`MultiEdit`/`NotebookEdit`. A task that edits with a heredoc, `sed -i` or a python one-liner leaves it empty, and the refresh exited as though the session had changed nothing — silently, in milliseconds, printing nothing. Observed on a real project: over 90 minutes the Stop hook ran nine times while three baseline findings were fixed, verified and covered by regression tests proved red first; `changed-files.txt` was never created and the baseline still reported all three as `open`. Git sees those edits, so it is now a peer source rather than a `--force`-only fallback. A working tree that stays dirty across turns is fingerprinted after the ignore filter, so reading git costs nothing when nothing moved and an untracked cache file appearing under `graft/` or `dist/` does not read as a new changed set.
- The generated `verify.sh` now runs the end-to-end suite when the repository declares one. `test:e2e` and `e2e` were never candidates, so a repository could keep its whole integration layer outside the Stop gate with nothing saying so. Observed on a real project: a session ran with 42 of its 54 e2e suites red while the gate reported green on every Stop, and a flake that had lived in those suites for months was structurally invisible to it. The step goes last, after the build, so the cheap checks still fail first. A monorepo that declares e2e only inside a workspace package is now named at initialization with the one root script that would put it in the gate — reported rather than wired up, because inventing the filter command would make a suite whose infrastructure the preflight does not start block as though the code were broken.
- The repository analysis no longer files findings about whether the harness itself is running. It executes with the repository as its working directory and `--tools "Read,Glob,Grep"`, so it cannot see `~/.claude` — where every hook, marker and setting actually lives. One project's baseline therefore carried a finding saying the promised automatic refresh was not wired, reasoning from a project `settings.json` with no harness hook and from two absent `.claude` markers that the harness removes on purpose, since an in-repo marker let a clone grant itself permission to run its own `verify.sh`. Both prompts now state that the wiring is out of scope and that the absence of those markers is not evidence. `.claude/verify.sh` and `.claude/preflight.sh` remain fair game for what they do, or fail to do, for the repository.
- Added an `invalid` finding status, so a false positive can be closed. The vocabulary covered a claim that was true and got fixed (`resolved`), true until the ground moved (`stale`), and true but carried on purpose (`accepted`) — and had no word for one that was never true. The only ways to close it were to hand-edit a generated file, which the harness tells people not to do, or to leave it open forever; the finding above sat open for exactly that reason. `invalid` is archived rather than active, renders under **Withdrawn findings** with what the original claim got wrong, and is deliberately kept rather than deleted so the title-key dedup stops a later analysis from filing the same false positive again.
- Re-initialization now keeps finding identity instead of renumbering everything. `render-project-analysis.mjs` allocated `F001…FNNN` from the position in the new response and reset the counter, so every rerun renamed every finding and discarded every decision anyone had recorded about one. A real project shipped a source comment pointing at "(F004)" for a finding its baseline by then called F001, and an accepted risk came back demanding action. A finding is now matched to the previous baseline by normalized title and keeps its number; new ones are allocated from the persisted `next_finding_id`, never from the current maximum, so a number retired by the retention cap is never handed to a different finding. `accepted` and `invalid` survive a rerun — they record a judgement no analysis can re-derive from source — and a decided finding the new analysis does not re-report is carried forward rather than dropped. A missing or corrupt prior baseline degrades to fresh numbering instead of aborting initialization.
- A finding that is real but not worth the fix is now filed as such instead of competing with the ones that are. The three rating axes measure harm and nothing else: nothing asked what a fix costs, so a trivial weakness that would take a cross-cutting refactor to remove printed exactly like a one-line bug — and a model told to look for risks fills the ten slots it is given, every run, forever. Prohibiting invention was already written down; authorizing an empty result never was, so the ceiling read as a quota and the findings worth doing lost their signal among the ones nobody was ever going to do. Findings now report a fourth grounded fact, `fix_cost` (`single_site` · `contained` · `invasive`, defined in files and call sites and costed against the recommendation actually written), and `tools/severity.mjs` crosses it with the computed rating: `low` at contained or invasive, and `medium` at invasive, are filed under **Carried findings — not worth the fix**; everything at `high` or above stays active work at any cost. Carried findings are recorded with a count rather than dropped, keep their own retention budget of 10 instead of consuming the 20 active slots, and a finding whose fix cost never arrived stays active work — nothing is demoted on a fact nobody supplied, and a baseline written before this axis existed upgrades with its whole tail intact. Both prompts now state that zero to three findings is the ordinary result and that an empty list is a valid answer.
- Every baseline finding now carries a worked example, and `detail`/`recommendation` finally have a contract. The schemas described `impact`, `trigger` and `blast_radius` in careful detail and then asked for `detail` and `recommendation` as bare `{ "type": "string" }` with no description at all — so the rating was calibrated and the prose was whatever the model felt like, which is how a baseline ends up full of findings nobody can judge. Severity says how bad the consequence would be; it never says what actually goes wrong, and a reader given only a level has no grounds to throw a finding out. Findings now report `example`: one concrete run that ends badly, with a named actor, the step that fails and the wrong state left behind. `detail` is specified as the mechanism in causal order, `recommendation` as the smallest change that removes the harm. A review that restates a finding inherits the stored example instead of blanking it, the same way `detail` already did, and a finding that arrived without one renders `**Example.** Not provided.` rather than reading as though its mechanism were self-evident.
- The preflight no longer misses a Docker Compose stack the project drives from a root-level script. A compose file alone is not consent to start it, so the preflight looks for the project referring to compose first — but that search covered only `package.json` and `scripts/`, and the launcher usually sits in the root. A monorepo whose `start.sh` runs `docker compose up -d` therefore read as having no stack: Docker Desktop was started, Mongo never was, and the preflight reported "passed" — after which 75 database-backed tests failed on a 5s connect timeout and the run blamed the code for a stack nobody launched. Root-level `*.sh` and `Makefile` now count as the same evidence. Observed on a real project whose Mongo and LocalStack containers had to be started by hand.
- Finding severity is computed from reported evidence instead of asked of the model. The schemas offered `critical|high|medium|low` and nothing anywhere — not the prompt, not the schema, not the renderers — said when to use which, so the same finding drifted between runs, two projects' `medium` meant different things, and the retention cap in `render-baseline-refresh.mjs` silently pruned findings by that drift. A rating with no written scale reads exactly like a calibrated one. The model now reports three grounded facts — `impact`, `trigger` (what must happen for the *harm*, not for the code path) and `blast_radius` — and `tools/severity.mjs` derives the level from a table that `tests/severity.test.mjs` pins cell by cell. The blast-radius modifier can never produce a `critical`, because a harness that is system-wide by nature would otherwise inflate every latent risk it has to the top level. Each rendered finding shows the axes it was rated from, and a finding whose axes never arrived reads `NOT MEASURED` rather than dropping to `low` as it used to.
- Added an `accepted` finding status. A real risk the project had decided to carry had nowhere to live, so the only way to express the decision was to understate the severity — which is how this repository's own documented `verify.sh` trust boundary came back rated `low`. The rating now states the risk and the status states the decision; accepted findings render in their own section instead of nagging from the active list every session.
- A dependency-free Node repository is no longer unverifiable. A repository that ships no `package.json` by design — this harness is one — read as `Generic`, so the generated `verify.sh` was the stub that exits 3, the Stop gate could never be earned, and editing `verify.sh` by hand did not help because the next initialization regenerates it unconditionally. `*.test.mjs`/`*.test.js`/`*.test.cjs` outside `node_modules` now select Node's own test runner (`node --test`), checked after the real manifests so a repository carrying both still verifies as the stack its manifest declares. Observed on this repository, whose own self-test suite the gate could not see.
- Both READMEs now state the reasoning behind the harness rather than only its behaviour, and draw its control flow. The document listed what each hook and file does but never why any of it is shaped that way, so the two decisions that matter most — why an unavailable tool must not block and why verification cannot be enforced by asking — read as implementation trivia instead of the reason the gate survives being installed. Added `Origin`, `Boundary`, a twelve-point `The engineering principles, and why` deriving each rule from the failure it prevents, `Repo layout`, and four Mermaid diagrams covering initialization, the session loop, test-rule generation and the finding state machine. The `Tests` section now separates the three things that share the word — the path-scoped policy that constrains how Claude writes tests, how the repository's own testing strategy is read into a generated rule, and the 120 tests this repository runs against itself — with a table naming what each test file pins.
- Rule-name reuse now compares the area a rule covers, not the exact spelling of its globs. The scope matcher required identical glob strings, so the same UI rule came back as `app/*.css` on one run and `app/**/*.css` on the next and was deleted and re-added under a new name over one character. A `**` segment says how deep a glob descends inside an area, never which area is meant, so it is dropped before comparing — and only before comparing: the frontmatter written to the file keeps the glob exactly as the model wrote it, because there the depth decides which files load the rule. Observed on a real project where three of six rules were renamed with no change in content.
- The repository analysis now writes its prose in the language the repository itself uses, and keeps that language across re-initializations. Nothing pinned it: three runs on the same Spanish-language repository within one hour produced Spanish rule bodies, then English ones, rewriting every rule file at once and leaving a diff nobody can read. The prompt now states the rule and tells the model to read an existing `.claude/rules/harness-*.md` and follow its language; the schema asks for the filename slug in the same language as the title, which is how a Spanish filename ended up wrapping an English rule.
- A full re-analysis no longer renames every rule file. The model names the topic freely, so the same group came back as `data-layer` on one run and `acceso-a-datos-y-cache` on the next — six deletions and six additions in the diff, with nothing to show what actually changed. The declared `paths:` scope is the steady part (measured across two real runs on the same repository: four of six path sets byte-identical, the other two only widened), so a rule group whose scope equals, contains or is contained by an existing rule file now inherits that file's name. A genuinely different grouping still gets a new one.
- The generated preflight no longer starts local infrastructure silently and walks away. `init-project.sh` is a one-shot command, so it now records what the preflight started and stops it afterwards, leaving the machine as it found it; a stack that was already running is never touched. The Stop gate deliberately keeps leaving it up — restarting Supabase before every task would cost far more than the gate is worth — so there the preflight says out loud that it left it running and prints the command to stop it. Reported by a real project's own analysis, whose stated policy is that Supabase stays down by default.
- The engineering standard now requires a finished change to be reported by listing the tests that cover it — each by name, what it asserts, and which broken behaviour it would catch — with pass counts last. A suite is green when nothing exercises the new behaviour just as surely as when everything does. It also states that a new test must be shown to fail against the unfixed code.
- The repository analysis now shows what it is doing while it runs. `init-project.sh` printed "Analyzing repository architecture..." and then nothing at all for several minutes, because `--output-format json` emits its first byte only after the final turn: a working Opus run and a hung one looked identical, and the natural response to an init that looks hung is to kill it halfway through, after the Stop markers have already been revoked. The call now streams (`--output-format stream-json`) through `tools/stream-progress.mjs`, which reports elapsed time, turn against the 40-turn budget, the file or pattern currently being read, tool-call count and accumulated thinking tokens, and hands the renderers the same result object the buffered format produced. A stream that ends without a result event is now an error instead of a partial analysis rendered as a complete one, and the CLI is no longer left waiting three seconds for stdin it never receives.
- Fixed generated rule files gaining an extra `harness-` prefix on every re-initialization: `harness-data-layer.md`, then `harness-harness-data-layer.md`, then `harness-harness-harness-data-layer.md`. The analysis reads the repository, so on a rerun the model saw the previous run's filename and echoed it back, and the renderer prefixed it again. Observed on a real project at the third run. The prefix is the harness's ownership marker and is now stripped from whatever the model supplies, so a rerun replaces a rule instead of renaming it. The schema also states the contract, and `tests/render.test.mjs` pins idempotence.
- The harness no longer lets a repository grant it permission to run that repository's own code. The hooks are installed globally and fire in every repository the user opens, and two steps execute repository-shipped scripts: the Stop gate runs `.claude/verify.sh`, and initialization runs `.claude/preflight.sh`. Both enabling decisions were read out of the repository, so a freshly cloned repository could switch the gate on for itself and have its `verify.sh` executed with the user's credentials — triggered by nothing more than asking Claude a question.
- `verify-on-stop` and `baseline-refresh-on-stop` moved from `<repo>/.claude/` to `~/.claude/harness-runtime/<project>/`, where only `init-project.sh` writes them and only after verification passed once. Markers found inside a repository are reported and removed, never migrated: migrating one would mean trusting exactly the file a clone can ship. The Stop hook names the fix so a project upgraded from an earlier version does not go quiet without saying why.
- A `.claude/preflight.sh` the harness did not generate is preserved but no longer executed. The previous check asked "did I write this file?" and preserved anything else — correct as data safety, wrong as a permission decision, because "not written by me" covers both "the user customized it" and "it arrived in the clone". Contents are untouched; the executable bit is cleared, which is what `init-project.sh` and the generated `verify.sh` already test before running it. `--trust-preflight` approves it and records its hash, so a preflight changed by a later `git pull` needs approving again.
- Added `tests/consent.test.mjs`: a repository fixture that ships its own markers, verify.sh and preflight.sh and proves none of them executes, plus the approval path, the hash withdrawal and the assertion that no shipped hook enables itself from a repository-controlled path.
- Graft integration now reports the evidence it actually obtained instead of the fact that wiring ran. `GRAFT_STATUS="passed"` was set on `graft init` alone and written into the analysis prompt and the run summary, so a repository whose graph answered nothing produced a prompt identical to one where every query landed — a groundless analysis read exactly like a grounded one. The status is now `indexed` or `wired-but-empty`, and both the prompt and the summary carry one line stating whether the repository map was empty and how many of the four structural queries returned anything.
- When no structural evidence was obtained at all, the analysis prompt says so explicitly rather than omitting the section, and instructs the model to prefer reporting less over inferring structure it could not verify. The incremental refresh does the same, and distinguishes "Graft not installed" from "Graft returned nothing for these files" — previously both became an absent section that reads like a small blast radius rather than an uncomputed one.
- The initializer now attempts `graft build --lsp` after wiring, which adds compiler-grade call edges from an installed language server. `graft init` builds parser-grade edges only, which silently drops aliased and re-exported callers. The pass is optional and slower, so its outcome is recorded either way and a missing language server is not treated as a failure.
- `VERSION` is now the single source of truth for the release string, is installed to `~/.claude/harness/VERSION`, and is read back by the installer's banner and the initializer's error messages. It previously had zero consumers while "v6" was restated in five places. The per-release feature paragraph the installer printed was deleted rather than pinned: it has to be rewritten every release, and the one release it is not rewritten, it lies.
- Added `tests/version.test.mjs` and `tests/graft-evidence.test.mjs`, the latter driving the initializer against a stubbed Graft to assert what the harness reports about a graph that answers nothing.
- The installable payload is now derived from the tree instead of listed inside `install.sh`. A file added under `src/harness/`, `src/rules/`, `src/agents/`, `src/skills/`, `src/hooks/` or `tools/` was previously committed, reviewed and documented and then silently never copied — no error, exit 0. Verified before the fix: a second agent, a second skill and a new prompt file all failed to install. `uninstall.sh` derives the hooks it removes from the same tree.
- The reviewer agent and review skill moved into the `harness-` namespace (`harness-engineering-code-reviewer`, `harness-engineering-review`), so `rules/`, `agents/` and `skills/` under `~/.claude` now have an ownership boundary the installer can prune. Reinstalling removes harness-owned files that upstream renamed or dropped — previously an obsolete rule kept loading as an instruction in every session forever — and removes the two pre-namespace names, so upgrading no longer leaves a second, stale reviewer alongside the new one. Files outside the namespace are never touched.
- The executable bit is derived from the source file rather than a second hardcoded list of which payload files are scripts.
- Added `tests/payload.test.mjs`: adds a file to every payload directory and proves the real `install.sh` and `uninstall.sh` round-trip it, plus the namespace prune, the user-file boundary and the pre-namespace upgrade path.
- CI now runs the full suite on macOS as well as Linux, and adds a job that executes it under the real `/bin/bash` 3.2. Bash 3.2 and BSD-userland support was a documented requirement verified by nothing, while the two most recent shell regressions were macOS-only and one of them passed `bash -n` on the machine that shipped it.
- The shellcheck job derives its file set from `git ls-files '*.sh'`, so a script added under a new directory is linted rather than silently skipped. The workflow also declares least-privilege `contents: read`.
- Fixed `refresh-baseline.sh` enabling `errexit` where it meant to restore it. The script runs under `set -uo pipefail` with no `-e`, so `set -e 2>/dev/null || true` turned errexit on for the rest of the run, defeating the fail-soft contract and able to abort between the paired `.md` and `.json` writes, leaving finding IDs in one that are absent from the other.
- Added `tests/schemas.test.mjs`, covering the two JSON schemas the scripted Claude calls depend on: they parse, they survive the newline stripping the callers apply, they close their top level, every `required` key is defined, and every key they ask the model for is one the matching renderer actually reads. A malformed refresh schema previously hit the fail-soft path, so the living baseline died while every Stop printed "refresh deferred" and exited 0.
- Added a root `CLAUDE.md` recording the constraints a change to this repository must not break. The harness's whole premise is putting a project's real constraints in front of the agent before it writes code, and it had never done that for itself.
- The Stop gate no longer reports a check it could not run as a defect in the change. Exit `3` (no verification strategy applies) and exit `127` (a required command is missing) are announced with their remediation and do not block; every other nonzero exit still blocks. Previously a developer without Docker was told to "fix the verification errors" on every Stop, with no edit that could clear it — the most direct route to deleting `.claude/verify-on-stop` and losing the gate entirely.
- The same treatment for the two conditions the hook detects itself: an enabled gate with no verification command configured, and a `verify` script with no package manager available, are now reported rather than blocking.
- Stop verification falls back to the PostToolUse edit record when git reports a clean tree, so a task that edits files and then commits them is still verified. The record is therefore written whenever either gate is enabled, and Stop verification clears it when the baseline refresh is off.
- Fixed the PostToolUse hook discarding every edit whose path reached it through a symlinked ancestor, which on macOS silently dropped every edit in a repository under `/tmp` or `/var`.
- `init-project.sh` now teaches git to ignore Graft's generated `graft/` directory. Left untracked and unignored, it made `git ls-files --others` permanently non-empty, so the "nothing changed" fast path never fired and the full verification suite ran after every Stop — including sessions that only answered a question. Repositories that deliberately track `graft/` are left alone.
- Added `tests/hooks.test.mjs`: behavioural coverage for both hooks, including the exit-code contract, the clean-tree-but-committed case, and the agreement between the ignore list in `mark-baseline-dirty.sh` and the one in `refresh-baseline.sh` that two comments already claimed was tested.
- The living baseline no longer grows without bound. Retention is capped at 20 active and 15 resolved/stale findings, dropping the lowest severity first, and a new finding is now deduplicated on a normalized title, so a reworded finding is not appended beside the one it restates. Pruning is reported rather than silent.
- Finding IDs are allocated from a persisted `next_finding_id` counter. Capping frees an ID, and allocating from the current maximum would have handed that number to a different finding later, breaking the stable-identity invariant.
- Generated rule bodies are sanitized before they reach the files Claude Code loads as instructions in every session. A leading `@`, which Claude Code resolves as a file import, is neutralized, and markdown link and image targets are stripped while the link text is kept. Paths, globs and filenames were already sanitized; bodies passed through whitespace collapsing only.
- `init-project.sh` names each generated rule file instead of only counting them, and says they load as instructions in every future session, so they get read once before the first task.
- Uninstall restores settings before deleting anything. The step that can fail for an environment reason ran last, after the global files were already gone, and the installed copy of the helper it needs lives inside a directory the removal wipes — so a missing helper or missing Node left the hooks in `settings.json` pointing at scripts that had just been deleted, with no message saying so. The helper is now also looked up in `~/.claude/harness-tools/`.
- `claude-opus-5` / `high` were restated in six places, of which only `HARNESS_DEFAULTS` is authoritative. `install.sh` now reads the values back instead of printing its own copy, and the remaining machine-readable copies — `settings-hook-snippet.json`, which a user copies by hand, and the two shell scripts' analysis fallbacks — are pinned by test.
- Added `tests/render.test.mjs`, covering the renderers' path, glob and filename sanitization and their finding-identity logic; `tests/init-project.test.mjs`, which runs the generator and asserts the `verify.sh` it produces parses, is executable and carries the Dockerfile lint block after the preflight line; and `tests/defaults.test.mjs`, which pins every copy of the harness defaults.
- `init-project.sh` no longer aborts on macOS Bash 3.2 when a repository has none of the conventional top-level source directories (`apps`, `packages`, `src`, `services`, `libs`, `modules`, `docs`). Under `set -u`, Bash 3.2 treats an empty array expansion as an unbound variable, so the fallback description was never reached.
- Uninstall now restores the `model` and `effortLevel` that were set before the first install instead of deleting them. Previously a user with a custom model silently lost it on install/uninstall.
- A value the user sets after installing is treated as deliberate and survives uninstall.
- Uninstall no longer leaves empty `hooks` containers behind, so a settings file it created nothing in round-trips back to its original content.
- `settings.json` is now written through a temporary file and an atomic rename, so an interrupted or failing write cannot truncate it. File permissions are preserved.
- A malformed `settings.json` is now reported as a single error instead of a raw stack trace, and is left untouched.
- Added round-trip tests for install and uninstall under `tests/`.

## 6.0.0

- Added automatic local-environment preflight through `.claude/preflight.sh`.
- Verification now distinguishes environment failures from code/test failures.
- Supabase projects automatically start the local stack when it is configured but stopped.
- On macOS, the preflight can start Docker Desktop and wait for it to become ready.
- Repository-declared Docker Compose infrastructure can be started conservatively when project scripts explicitly reference Compose or `.claude/auto-compose` is present.
- Stop verification reuses the same preflight, so local infrastructure can recover automatically during normal Claude Code work.
- Added `HARNESS_AUTO_INFRA=0` to make infrastructure startup check-only, plus timeout environment variables for Docker and Supabase.
- Graft is now checked against npm during install and project initialization. The harness upgrades only when npm has a newer version and never downgrades a locally newer Graft build.
- Preserves a custom `.claude/preflight.sh`; only harness-generated preflight files are refreshed automatically.

## 5.0.0

- Added living engineering baselines with stable finding IDs.
- Added `.claude/engineering-baseline.json` as machine-readable finding state.
- Added a global PostToolUse hook that records files edited by Claude Code without calling a model.
- Extended the Stop quality gate so baseline refresh runs only after successful verification.
- Added incremental Graft + Claude Opus 5 high baseline revalidation.
- Existing findings can become OPEN, CHANGED, RESOLVED, or STALE.
- Incremental analysis can add concrete NEW findings from the changed blast radius.
- Unrelated findings are not re-audited on every task.
- Baseline refresh failures are fail-soft and retried later; verification failures remain blocking.
- Added full-reanalysis signaling when a change appears to materially alter project architecture.
- Added explicit global policy that baseline findings must never be treated as authoritative over current source and tests.
- Fixed project slug generation so archive directories no longer gain a trailing underscore from newline translation.
